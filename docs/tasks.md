# Task feature

`/tasks` uses the existing RTL design, authentication, navigation, cards and buttons.
It uses the authenticated user's existing profile interests and skills as dropdown
choices. Gemini determines the category and generates the actual task requirements,
instructions, time and reward points. All categories share comment, file, folder,
ZIP and optional link submissions. No new Profile, Skills or Level pages are built.

## Configuration

The local `.env.local` contains `GEMINI_API_KEY`, `GROQ_API_KEY` and a dedicated
`TASK_DATABASE_URL`. All are server-only and ignored by Git. Both provider keys
were accepted by their read-only model-list endpoints. No live generation or
account test was performed. Deployment needs these same environment variables,
in addition to the existing Supabase authentication configuration.

`GEMINI_TASK_MODEL` overrides the task model; otherwise `GEMINI_MODEL` or
`gemini-3.5-flash` is used. Gemini is attempted first; if it fails, times out or
returns invalid output during generation, the task context is sent to Groq.
Evaluation uses Gemini only, including actual images and documents; it never
silently switches to a text-only provider.
`GROQ_TASK_MODEL` overrides `GROQ_MODEL` or `openai/gpt-oss-120b`. With only one
key configured, only that provider is used for generation. Groq uses strict structured JSON;
server validators enforce the same field, list and score limits for both providers.
Each saved task/review records the actual provider and model in `ai_model`.
Requests use key headers and structured JSON output. Keys, raw provider errors,
written answers and session tokens are never
included in logs or client configuration. The public Supabase root certificate
in `lib/tasks/database-ca.js` enables certificate-verified TLS. If the project's
CA changes, set `TASK_DATABASE_CA` to its PEM certificate (escaped newlines work).

`scripts/setup-tasks.mjs` applies only the Task migration, records its version,
and provisions a dedicated non-superuser login that cannot bypass RLS. It reuses
the existing database connector for setup only; app requests never read connector
files or use the administrative database credential. Re-running setup keeps the
existing login and password. The application pool has one connection per instance
and bounded connection/query timeouts.

If a dedicated Task password drifts from the saved local credential and PostgreSQL
reports `28P01`, `node scripts/setup-tasks.mjs --repair-login` restores the existing
random credential for `task_api` only. It checks that the saved connection targets
the same project and that the role still enforces RLS. It does not rotate project
credentials, elevate privileges, or change user accounts.
After a repair, verification retries a temporarily cached pooler password for up
to six attempts. Query timeouts and idle-pool error handling keep a dropped
connection from hanging requests or crashing the application.

## Ownership and scoring

The migration creates `tasks`, `user_tasks`, `task_submissions`, `task_feedback`
and a private table for AI request leases. All enable RLS. Each request validates
Supabase Auth, derives the user ID on the server, and sets transaction-local
identity for the restricted database login. The client cannot supply an owner ID.
Foreign keys bind ownership across all related records.

Authenticated users may read only their own rows, start their own tasks, and
insert their own submissions. Task generation and feedback writes use the trusted
server role. Browsers cannot create AI task templates, change scoring criteria,
set scores or earned points, or directly mark a task submitted/reviewed.
Database triggers enforce Available → In Progress → Submitted → Reviewed;
submission and feedback transitions happen atomically with their records.

Task reward points are generated by AI (10–300). Gemini returns `score`, `passed`,
`points`, `strengths`, `issues`, `improvements`, `criteria_breakdown`,
`evaluation_status` and an explanation. Server and database enforce the five
weights: requirements 30, quality 25, execution 20, evidence/explanation 15,
creativity/problem-solving 10. The score must equal the exact sum. Passing requires
70/100, disclosed in the UI. Earned points are `round(task.points * score / 100)`.
Cannot-evaluate results have null scores, no rubric grades and no earned points.
Earlier feedback is preserved without inventing a historical rubric. Unique constraints
prevent duplicate submissions and point awards. Total points are derived from
saved feedback, rather than an independently mutable profile total.

AI calls happen outside database transactions. A short database lease prevents
concurrent AI requests per user, with a five-second cooldown, a 180-second crash
recovery expiry, a maximum of 20 active tasks and 20 generated tasks per rolling
24 hours. Each provider gets one attempt with a 45-second timeout. Generation failures
do not create fabricated tasks. Answers are saved before evaluation; failed
evaluations remain Submitted and can be retried without resubmitting the answer.

Mutation routes require same-origin JSON or bounded multipart requests and validate field sizes,
UUIDs, categories, difficulties and HTTP(S) work links. URL credentials are
rejected. Work links are never fetched: there is no URL-context or browsing tool,
no SSRF request, and no claim that the linked work was independently verified.
The form discloses that the comment and actual readable files go to Gemini.
History shows fully evaluated, partially evaluated or cannot be evaluated with
trusted inspection limitations and the model's explanation. Saved submissions
can retry provider failures without uploading again.

## Future connections

`recommendationContext()` in `lib/tasks/server.js` is the replaceable input
adapter. It uses profile interests/skills, validates selected dropdown values
against the current authenticated profile, and includes recent task titles.
`tasks.profile_id` now identifies that profile; `tasks.skill_id` remains nullable,
with no dependency on future tables; `generation_context` stores the input
source and `recommended_by_ai` records provenance.

`task_submissions.attachments` stores server-generated metadata for private
Supabase Storage files. Uploads allow 40 relevant files, 6 MB per file, 20 MB total;
folder selections can include up to 200 entries before exclusions. Dependency,
build and credential files are omitted. Images are decoded (up to 16 megapixels),
resized to 1600 pixels and stored as WebP; actual image and PDF bytes go to Gemini.
UTF-8 text and source files are read, including files inside ZIPs. ZIPs are never
extracted to disk or executed; traversal, symlinks, encryption and excessive
expansion are rejected. ZIP inspection allows 200 entries and 20 MB expanded.
Evaluation supplies up to eight images/documents (12 MB combined) and 120,000 text characters,
and discloses omissions. Unsupported formats are stored with explicit limitations.
Links are never fetched. Files remain private, immutable, owner-scoped and linked
to submissions. Downloads use an authenticated API, without public URLs.

`node scripts/setup-task-evaluation.mjs` applies the upload/rubric migrations.
Offline checks: `node --conditions=react-server --test scripts/test-task-ai.mjs scripts/test-task-evidence.mjs`.

## API

- `GET /api/tasks?offset=0`: active tasks, paginated history and earned-point totals.
- `POST /api/tasks/generate`: `{ interest, skill, difficulty }` from profile values.
- `POST /api/tasks/:id/start`: start an available task.
- `POST /api/tasks/:id/submit`: multipart `description`, `workLink`, repeated `files`, then review.
- `POST /api/tasks/:id/review`: retry evaluation of a saved submission.
- `GET /api/tasks/:id/files/:index`: private authenticated download.

All API routes validate authentication independently of Proxy and return private,
uncacheable responses. No API accepts user IDs, scores, points, roles or AI keys.
